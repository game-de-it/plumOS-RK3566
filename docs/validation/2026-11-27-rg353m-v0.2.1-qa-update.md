# RG353Mでの標準System Update実機検証

2026年11月27日（JST）。RG353Mを、ユーザーがTF1に書き込んだ共通SD試験イメージv0.2.0から起動した。実機の `/flash/SYSTEM` のSHA-256は `5439d0705e84c91b5b647b012ddbccecc90de725687ca605439026c47066a053` で、検証済み成果物と一致した。[共通SD試験イメージの記録](2026-11-27-v0.2.0-test-image.md)

## 配布物と開始時の状態

| 項目 | 確認値 |
| --- | --- |
| 更新アーカイブ | `plumos-rk3566-runtime-0.2.1-qa.tar.gz`（599バイト） |
| SHA-256 | `38bbc88e66ad7db9c9039a3fd6d6fc36c0e74a5c80ef45776163334a21bc80a8` |
| 署名マニフェスト | 機種ID `rk3566`、アーキテクチャ `aarch64`、適用元 `0.2.0`、適用先 `0.2.1-qa`、種別 `runtime` |
| 同梱Ed25519公開鍵のSHA-256 | `ffd8ac7879b6cdf9432f423c5670336709ffa802e2c63df89c891ac6ec8243a1` |

出荷版の `build-runtime-update.py` と正式署名鍵で、ランタイムの `VERSION` だけを更新する差分を作成した。配布ファイルと同じ `.sha256` をMacで照合し、ADBでファイルを `PLUMOS/updates/`（実機の `/storage/user/updates/`）へコピーした。配置後もアーカイブのSHA-256は一致した。開始時はOS本体・ランタイムともに `0.2.0`、更新の保留状態は空。使用中の公開鍵と更新プログラムはSYSTEM内の出荷時ファイルと一致しており、公開鍵の手動導入は不要だった。

## 実機での適用結果

1. 実機で動作しているフロントエンドにADB経由で通常のボタン入力を送り、内蔵画面の `START → System Settings → System Update` を選択した。フロントエンドのログに配布アーカイブの名前、SHA-256、適用元 `0.2.0`、適用先 `0.2.1-qa`、`result=ready` が記録された。
2. メニューの要求で本体が自動再起動し、USB ADBが再接続された。起動IDの変化を確認した。更新ジャーナルは `status=healthy`、最終結果は `runtime_healthy` で、保留状態は解消された。
3. 再起動後、`INFORMATION` の実機スクリーンショットで `PLUMOS: 0.2.1-QA` が表示された。内蔵画面のフォントは英字を大文字で描画する。ランタイムの `VERSION`、更新マニフェストとアーカイブ名では `0.2.1-qa` が保持され、ベースOSは `0.2.0` だった。公開鍵と更新プログラムは引き続きSYSTEM内の出荷時ファイルと一致し、ブートSYSTEMのSHA-256も成果物と一致した。

| 領域 | 更新前後の実機マウント |
| --- | --- |
| TF1 p5 | `/dev/mmcblk1p5` を `/storage/user` に読み書き可能でマウント。ラベル `PLUMOS`、UUID `7E1E-0DCD` は同一。 |
| SD2 | `/dev/mmcblk2p1` を `/run/media/sd2` に読み書き可能でマウント。UUID `1D0C-1A62` は同一。`Roms` と `BIOS` は同じSD2上のディレクトリを参照。 |

この試験では、配布アーカイブを利用者領域に置く手順、標準メニューの署名検証、実機の自動再起動、最終表示までを確認した。差分の内容はバージョン情報であり、エミュレータや機種別ハードウェア機能の動作試験は別途扱う。
