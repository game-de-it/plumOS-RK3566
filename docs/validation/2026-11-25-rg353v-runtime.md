# RG353Vのエミュレータ・Apps・電源管理

USB接続時の起動対策を含む共通IMGで、RG353Vの内蔵640×480パネルとTF2を使用した。SYSTEMは `bb41fc6bcc9c8b8869ce8848e156ac07202d53a765fadd8cd4053b488b817da0`。エミュレータの検体はRGB30の実機表と同じセットを使い、設定とセーブを試験用の一時領域に分離した。実機カタログは196プロファイルで、互換性を確認済みの検体がある174件を対象にした。[RG353Vの起動確認](2026-11-25-rg353v-usb-cold-boot.md) · [RGB30の検証基準](2026-11-24-rgb30-emulators.md)

初回の代表34件では、全件でフレーム提示と内蔵PCMの進行を確認した。Gambatteは533×480で左右中央、QuickNESのRetroArch版はコア指定の比率で627×480、Game Gearは640×480で表示した。GBAのRetroArch版とPicoArch版は3:2で約640×426、PPSSPPはPSPの比率で約640×363の中央表示だった。DraStic、PCSX-ReARMed単体版、OpenBOR、Pyxelでも実機画面を捕捉した。PCM進行はカーネル上の再生計測に基づく。

## エミュレータの起動試験

RetroArch 131件、PicoArch 36件、単体5件、Pyxel 1件、Ports 1件を実行した。再試験を含めて174件でフレームの表示と更新を、172件で内蔵PCMのハードウェアポインターの進行を確認した。2048とTI-83はどちらも画面が更新され、PCMは試験区間を通して `PREPARED` だった。残る22プロファイルには指定ROMセット内で対応する試験素材が見つからなかった。記録は代表タイトルの起動時点の計測で、各タイトルの全編の音と表示は未確認。[全196プロファイルの試験表](rg353v-emulator-matrix.tsv)

RetroArchの共通設定と計測で取得した設定値は `aspect_ratio_index = 22`（Core Provided）。DRMに出た矩形は内蔵画面の範囲に収まった。RetroArch版YabaSanshiroは初回の短い試験で描画と音声を検出できず、起動待ちを20秒にした再試験で『The Tower』の画面更新58.59 fpsとPCMの進行を確認した。OpenBORの『Dragon Ball』はタイトル付近でPCMを開き直し、その後は再生を継続した。

連続起動試験中、Mr.Boomは起動時に約10秒待ってから描画とPCMが進んだ。音声バッファを64 msから96 msに増やしても待ち時間は変わらなかった。再起動後の3回の試験では再現せず、約56〜58 fpsでPCMが進み続けた。起動待ちの原因は未確定。

Mr.Boomの起動待ちと各コアの音切れは、カーネルのXRUN記録とコアの実行間隔を使って再調査した。[音声の追加調査](2026-11-25-rg353v-audio-followup.md)

Virtual JaguarとBeetle PC-FXは、RGB30で同じ素材を使った試験と同様に、描画が約18 fpsと約35 fpsにとどまり、PCMのXRUNも観測した。Beetle Saturnも約24 fpsで、短い計測中にPCMが複数回再始動した。MicroW8、Mupen64Plus-Next、Uzeboxは14秒の再計測でもXRUNが発生した。

## スリープ

USB ADBで給電中にBubbleの電源メニューから `mem` を選び、JELOS由来の `s2idle` に入った。RTCで12秒後に復帰し、boot IDとBubbleのPIDが一致していた。復帰後はUSB ADBがケーブルの抜き差しなしで再接続した。

出荷用ランチャーとDRMブローカーを使い、ゲーム中に電源キーから開くメニューでSleepを選んだ。RetroArchのgpSP、PicoArchのQuickNES、PCSX-ReARMed、PPSSPP、DraStic、YabaSanshiro、OpenBOR、Pyxelは、RTC復帰後に同じ描画プロセス、フレームバッファの提示、PCMポインターの進行を確認した。復帰後に内蔵パッドと同じevdevへ試験入力を送った。

Music PlayerはWAV再生中にSleepし、同じプロセスで再生を再開した。File Manager、RetroArchのメインメニュー、Game Gear、PortMasterでも同じ描画プロセスに復帰した。Scraping、Pyxel Setup、Update PortMaster、Repair SD2は、Bubbleの同じ画面に戻りBで終了できた。復帰に使ったのはRTCで、物理電源ボタンによる復帰はこの試験では未確認。

## PortMaster終了後の電源操作

Portsの起動試験とPortMasterのスリープ試験で、試験プロセスの終了後にPortMasterのbindマウントが残った。旧SYSTEMでは、エミュレータを閉じて再起動しても、残留マウントによってフロントエンドのオーバーレイを解除できず、安全停止が中断された。PortMasterの既存の後片付け処理で解除すると、同じ手順で再起動できた。

plumOS initは電源操作時に、プロセスを停止したあとでPortMasterの `port.mounts` と `state.mounts` を確認し、記録されたマウントを既存のヘルパーで解除する。ヘルパーが対象の検証や解除に失敗した場合は、元の安全停止中断と復帰の経路を使う。

Dockerで修正版SYSTEM `e0ade7b9ff94efa02f7ebae7a96148e37ed543656de3f49723e40b2cacffdf71` を生成し、既存SDにADBで転送して試験起動した。実機で両方の記録ファイルに対応する残留マウントを再現し、USBを挿したまま安全再起動した。boot IDが変わり、修正版SYSTEM、Bubble、USB ADB、p5とTF2の読み書きマウントが復帰した。残留マウントがなく、修正版は既定として起動した。
