# RGB30r2のFEスクロール検証

720×720の内蔵画面で、既定テーマのトップ、NESのROM一覧、ギャラリーを調べた。従来版はplumOS-BubbleのFEを土台としており、plumOS-Bubbleの `a717463` にトップとギャラリーのアニメーション中だけガバナーを切り替える処理がある。ただしRK3566版の起動時の機種IDでは、この処理は実行されなかった。plumOS-Bubbleの `3dec38b` と `13c654d` と同じく、FEが記録するDRMページフリップ完了時刻を計測に使った。

RGB30のDRMモードは720×720で実測約59.9 Hzだった。SD2の同じNESライブラリーを使い、ADBから十字キー相当のevdev入力を送った。ページ切り替え、ROM一覧の上下移動、ギャラリーの左右移動の順で測定した。ギャラリーの比較には、左右入力に対応する最初のフリップの後、315 ms以内のフリップ間隔を集計した。同じ入力を左右6回ずつ送った。

| ギャラリーの条件 | アニメーション中の実効fps | 1回のVBlankで表示できた間隔 | 入力読み取りから最初のフリップまでの中央値 |
|---|---:|---:|---:|
| 従来の描画・`ondemand` | 26.3 | 0 / 94 | 33.30 ms |
| 従来の描画・`performance` 固定 | 29.9 | 0 / 108 | 33.29 ms |
| 描画を最適化・`ondemand` | 52.9 | 165 / 190 | 16.55 ms |
| 描画を最適化・アニメーション中だけ `performance` | 59.9 | 216 / 216 | 33.26 ms |
| 採用版。描画を最適化・アニメーション中だけCPUの下限を引き上げ | 59.9 | 216 / 216 | 16.53 ms |

従来の描画ではRGB30のギャラリー背景の描画コストが高く、最大クロックでも2回のVBlankを要した。DRM用のPNG描画を行単位にし、キャッシュ可能なメモリー上で描画してから、完成したフレームを一度だけDRMバッファーに転送する。トップの画面外タイルは描画しない。DRMのページフリップ完了待ちは継続し、次に描画できる時刻の計算では、1 µs刻みのループを省いた。DockerのARM64環境で、透過・切り抜き・拡大縮小・回転を組み合わせた59,904件を従来の描画と比較し、バッファー内容が一致した。

トップのページ切り替えでは、採用版の172間隔すべてが1回のVBlankに収まり、59.9 fpsだった。ROM一覧では343間隔中339が1回のVBlankで、59.2 fpsだった。ギャラリーでは移動の合間と静止時も含めると57.2 fpsだった。液晶の応答時間は計測に含まない。

採用版は通常のCPUガバナーを保ち、トップとギャラリーのアニメーション中だけ、現在の上限値までCPUの下限を引き上げる。実機では `ondemand` のまま下限が408 MHzから1,992 MHzへ上がり、キーを離してアニメーションが終わると408 MHzへ戻った。画面を閉じるときとゲームに描画を渡す前にも元の下限へ戻す。

採用版のFEをDockerのARM64ビルドに取り込んだ。SYSTEM `22045625b48dc8fcd904d0e03ebfbb289e85254466320037df5ebafbda7a2385` を、既存SDへADBで差分適用した。通常の起動経路で新しいFEとADBが立ち上がり、SD2上のNES一覧とギャラリーが表示された。ギャラリーが移動中の状態から『Binary Land』を起動し、QuickNESのゲーム画面と起動後のCPU下限408 MHzを確認した。ゲームをADBから終了してトップに戻し、SYSTEMを既定に設定した。更新前後でカーネル、RGB30のDTB、extlinux設定のSHA-256と、SDのパーティション一覧が一致した。

計測開始時にランチャーの実行権限が不足し、一度FEが停止した。権限を修正して計測を再開し、最終SYSTEMはPID 1から起動している。実機の結果はRGB30r2での確認。
