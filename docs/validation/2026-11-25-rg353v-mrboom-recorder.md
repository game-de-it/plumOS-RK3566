# RG353VのMr.Boom起動停止を記録する

Mr.BoomをFEから起動すると、RetroArchのランチャーが起動診断も開始する。起動後40秒間、約150 ms間隔でページフリップの時刻とシーケンス番号、出力先のALSA PCMの状態とポインターを確認する。ページフリップが3秒間進まなければ、直前の最大40サンプルとその後の状態を保存する。復帰後の採取は3秒、停止からの採取全体は最大20秒。DRMトレースには専用のインスタンスを使い、終了時に解除する。[前回の原因調査](2026-11-25-rg353v-audio-followup.md)

`ppoll` 中のメインスレッドと、記録開始後に見つかった他の待機スレッドについて、FD番号、イベントマスク、FDの参照先、`fdinfo`、タイムアウトを採取する。読み取りの前後でシステムコールの引数が変わったサンプルは破棄する。DRMトレースが使えない場合は、メインスレッドの同じ待ちが3秒続いたときに、トレースのエラーとともに記録する。

ログは本体の `/storage/plumos-rk3566/frontend/logs/mrboom-startup-stall.jsonl` に保存される。保持するのは最新の停止1件。正常に起動した回は新しい停止ログを作成しない。

## RG353Vでの確認

通常起動ではMr.Boomの動作中に診断が起動し、停止ログを生成しなかった。次に試験用のライブラリを一時的に読み込ませ、起動したゲームに6秒の `ppoll` 待ちを発生させた。診断ログの37サンプルで試験コードが開いた FD 11 を `anon_inode:[eventfd]` と特定し、`POLLIN` と6,000 msのタイムアウトを記録した。停止前はPCMポインターと画面のシーケンスが進行し、停止中はPCMが `XRUN`、ページフリップは0件だった。待機が終わるとPCMが `RUNNING` に戻り、ページフリップも再開した。復帰後3秒のサンプルと診断の終了を確認した。

Dockerで生成したSYSTEM `46645502d87a2762a251818ad8e86c8970ce2d1bdae85c457f4f07e11528f1fe` をADBで転送し、既存SDから試験起動した。通常起動と制御した待機の両方を確認後、同じSYSTEMを既定に設定し、FEとUSB ADBが戻っていることを確認した。

前回の約10秒停止は未再現。今回確認したのは、実機で制御した待ちを診断が採取できること。試験用のライブラリと停止ログは診断機能の配布物に含めていない。
