- RK3566専用のEd25519鍵を用意した。公開鍵のPEMファイルのSHA-256は `ffd8ac7879b6cdf9432f423c5670336709ffa802e2c63df89c891ac6ec8243a1`。新規ビルドではこの公開鍵を収録する。
- v0.1.1の出荷SYSTEMからランタイムを抽出し、正式公開鍵とランタイムのバージョンを差分としてパッケージ化した。Dockerで秘密鍵に対応する公開鍵を照合し、マニフェストの署名と配布ファイルのSHA-256を検証した。
- 改名前にRG503のv0.1.1で、出荷時の公開鍵がv0.1.2の署名を拒否することを確認した。TF1のPLUMOS領域に移行ZIPを展開し、FEのFile Managerから `Install-Update-Key.sh` を実行した。署名の検証と更新ファイルの検出が正常終了した。
- `START → System Settings → System Update` を実行し、自動再起動後にランタイムがv0.1.2に更新された。更新は `runtime_healthy` と記録され、同じパッケージの再適用は対応元バージョンの不一致で拒否された。
- TF1から試験に使った配布ファイルを除いて通常再起動し、ランタイムv0.1.2と正式公開鍵が維持されることを確認した。OS本体はv0.1.1。p5とSD2は更新前と同じ識別子で読み書き可能としてマウントされた。

## RK3566ファイル名での更新検証

- 署名済みアーカイブをバイト単位で保持したまま `plumos-rk3566-runtime-0.1.2.tar.gz` へ改名した。SHA-256ファイルの記載名も更新した。
- 出荷版v0.1.1のARM64 SYSTEMをDockerで展開し、実機と同じランタイムのオーバーレイをマウントした。更新前のSystem Updateは新しい名前のファイルを検出できなかった。
- 新しい移行ZIPを実行し、従来の公開鍵を使う環境と、正式公開鍵を導入済みの環境の両方で、新旧のファイル名を検出できることを確認した。新しい名前のアーカイブだけを置き、フロントエンドが使う `request-latest` で検出と署名検証、`apply-pending` で適用、`mark-healthy` で `runtime_healthy` を確認した。新ファイル名での実機再試験は未実施。
