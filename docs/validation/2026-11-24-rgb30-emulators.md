# RGB30のエミュレータとAppsの実機検証

RGB30の内蔵パネルは720×720。RG353Mと同じ起動経路を使い、既存SDのSYSTEMを試験起動で更新した。更新後はp5とTF2の `mmcblk2p1` を読み書きでき、起動後にWi-Fiへ自動接続した。

## 表示

DRMのフレームバッファから画像を取得し、表示矩形と合わせて確認した。PCMの状態とハードウェアポインターの進行を同時に記録した。

| 経路 | RGB30での表示 |
| --- | --- |
| RetroArch / QuickNES | NESの描画面は720×551、上端84 px。コアのアスペクトとクロップを反映した上下中央配置。 |
| RetroArch / Gambatte | GBの10:9を720×648で表示。上下36 pxずつの余白。 |
| RetroArch / gpSP | GBAの3:2で上下中央に表示。 |
| RetroArch / Genesis Plus GX | Game GearのLCDプリセットは640×480。上下120 px、左右40 pxずつの余白。 |
| PicoArch / QuickNES | 4:3の720×540、上端90 px。旧版は640×480を左上に配置していた。 |
| PicoArch / gpSP | GBAの3:2の画面を720×480で中央に配置。上下の余白は120 px前後。 |
| DraStic | 4:3の720×540、上端90 px。旧版は640×480を左下に配置していた。SDLの実表示サイズに合わせてGLESビューポートを設定した。 |
| PPSSPP | PSPの480×272の比率で720×408相当に配置。上下約156 pxの余白。 |

RetroArch、PicoArch、Pyxelは、RGB30でCPUガバナーの `policy0` が公開されない場合も起動できるようにした。利用可能な機種では従来のガバナー設定と復帰を行う。旧試験でSD上に置いたRetroArchランチャーとPicoArchバイナリは、SHA-256が一致するものを初回マウント時に退避した。既存SDの更新でも、SYSTEMの収録物を使うことを実機で確認した。

## 起動試験

現行のFEに登録された196プロファイルと試験表のキーを照合した。ROMセットから代表素材を用意できた174件を実行し、再試験を含めて174件の画面提示と172件のPCMポインターの進行を確認した。22件は試験素材なし。短い計測窓での描画・PCM測定で、各タイトルの全編やスピーカーの聴感評価は対象外。テスト時のシステム音量は20%。[プロファイル別結果](rgb30-emulator-matrix.tsv)

- 代表的なNES、GB、GBAでは約59 fps。Pyxelは約30 fps。PSPの『Star Soldier』は約59 fps。
- YabaSanshiroのRetroArch版は初回の短い計測で画面提示を検出できなかった。待ち時間を延ばした再試験で『The Tower』のタイトル映像とPCMを確認し、約59 fpsを記録した。
- 『The Tower』のYabaSanshiro単体版で約16 fps、Beetle Saturnで約24 fps。Beetle SaturnとVirtual JaguarとPC-FXの測定窓ではALSAのXRUNも記録した。
- 2048、TI-83の測定窓でPCMは `PREPARED`。ポインターの進行は観測しなかった。Atari 8-bitのAtari800は最初に選んだBASIC ROMでPCMが進まなかったため、『Yoomp!』で再試験した。タイトル表示、720×540の描画面、約41 fpsとPCMポインターの進行を確認した。
- 『Caverns of Mars』のヘッダーなしROMは、同じ16 KiBの複数のカートリッジ種別を旧コアが判別できず、黒画面になった。MAMEのソフトウェア一覧にあるCRC `8b9b2f5e` を照合し、標準16 KiBのマッピングを選ぶよう修正した。元のROMで720×540のタイトル表示、約40.8 fps、PCMポインターの進行、FNメニューの表示を確認した。FEの起動経路でも約41 fpsとPCMポインターの進行を確認した。[MAMEのAtari 800ソフトウェア一覧](https://github.com/mamedev/mame/blob/mame0251/hash/a800.xml#L1421-L1433)
- 同じ修正版コアでAtari 5200の『Millipede』を再試験し、タイトル表示とPCMポインターの進行を確認した。
- FreeJ2ME-PlusはシステムFontconfigが無い環境で起動時に例外が出ていた。同梱フォントを指定し、『Cento』が表示され、PCMポインターが進むことを確認した。
- RetroArch、PicoArch、DraStic、PPSSPPでゲーム中のFNメニューを確認した。
- OpenBORは初回の短い計測でXRUNを1回検出した。縦横比の修正版では、タイトル表示後の20秒で約59.7 fps、PCM開始1回とポインターの連続した進行を確認した。

Appsの試験中、自動入力がメニューからずれて電源オフを要求した。終了処理はランタイムのアンマウントで中断され、後続の試験では入力ごとにメニューの位置を検証した。試験SYSTEMの正常起動後、SD2が再度読み書き可能であることを確認した。

最初のエミュレータ表を取ったSYSTEMのSHA-256は `4a96a540923a0f95401ed8efcacfa478fc75e2e300cf59b0cc7ff5b5b20314d4`。Appsの修正版は `7698c019129144c63fcb76e8a2d1c99496644904ed06683ff564ef4b38531af1`。Atari800の修正を含む最終版は `960d20c102d53ceda7bd33fdc5a96d98eb52e38d71c2990215c3ca6f1fcf5469`。ARM64 Dockerで組み立て、Wi-Fi ADBで差分を送り、復元したSYSTEMのSHA-256を検証して試験起動した。最終版を既定に設定し、FEが復帰してp5とSD2が読み書きマウントされることを確認した。復旧に使えるよう、直前のSYSTEMもp4に保管した。ブートパーティション上のKERNEL、出荷用SYSTEMとDTBのハッシュは更新前後で一致した。試験後は音量設定を元の値に戻した。

Game Gearは640×480の内部描画と4:3を維持し、パネルの解像度に収まる矩形へ拡縮する。既存の並列描画で拡縮し、上下または左右の余白を黒で描く。Scrapingは説明が標準サイズで収まらない場合、その行だけ小さいフォントで描く。サムネイル名の一覧を取得できない場合のURL生成には、SYSTEM同梱のPythonを使う。PNG取得試験では、サムネイル名のキャッシュが空のまま、CRCで一致したNESタイトルのPNGを1件取得した。

## USBと試験用の接続

既存のUSBケーブルを接続した状態で、RGB30の充電器検出は `DCP=1`、`SDP=0`、UDCは `not attached`。ADB gadgetとFunctionFSは起動していた。gadgetの再起動とソフトウェアでのUSBロール変更後も同じ状態だった。MacからUSB ADBを開くには、データ接続として列挙される必要がある。

Wi-FiのSSHを使い、別のネットワーク名前空間でADBをループバックに限定して起動した。MacのループバックからSSH経由で接続し、`adb shell` と `push`、`pull`、転送ファイルのSHA-256を確認した。USBの抜き差しやSDイメージの再書き込みを伴わず、SYSTEMの更新と実機検証に使った。

`prototype/adb-over-ssh.py` は、この経路をSSHで認証済みのMacから開く。ADBプロセスは接続ごとに独立し、USB FunctionFSと実機のストレージマウントから分離する。`adb push` と `adb pull` は `/run` などの一時領域を使用し、実機のマウントを参照するシェルコマンドは `busybox nsenter -t 1 -m -n` で実行する。RGB30でSSH接続、ADB通信、ファイル往復と切断を確認した。

SSHのホスト名を `rgb30` として登録済みの場合の操作。

```sh
python3 prototype/adb-over-ssh.py root@rgb30
# 別のターミナルで実行
adb connect 127.0.0.1:15555
adb -s 127.0.0.1:15555 shell busybox nsenter -t 1 -m -n /bin/sh
```

同じJELOSカーネルのSYSTEMに含まれる `ipv6.ko` を `--ipv6-module` に渡すと、Mac側の同じ待ち受けで、ADB接続のたびに未ロードのモジュールを補う。実機再起動直後の未ロードをSSHで確認し、その後に同じ待ち受けへの `adb connect` と `adb shell` が成功した。ロード後も `wlan0` のIPv6は無効で、ADBは名前空間内のループバックで待ち受けた。

USB側では、接続したままDWC3のランタイム電源を一時的に有効化し、コントローラーが `device` モードで動作する状態でUSB gadgetの論理切断と再接続を実施した。復帰後も `DCP=1`、UDCは `not attached`、MacのUSBツリーにRGB30は現れなかった。試験後はランタイム電源の設定を元へ戻した。

エミュレータ表の音声欄は、RK817へのPCM転送を測定したもの。USB DACの実機の音と出力切替は未測定。

## RGB30の内蔵スピーカー無音

無音の報告時、実機は自動出力を選択し、ヘッドホン未接続、音量は20段階中20だった。PCMは進んでいたが、RK817の `Playback Path` は `SPK` だった。JELOS 20240206の機種設定に従い、RGB30の内蔵スピーカーに `HP`、ヘッドホンに `SPK` を割り当てた。RGB30とRG353Mについて、自動判定と明示指定を合わせて9ケースのルーティングを確認した。[JELOSのRGB30機種設定](https://github.com/JustEnoughLinuxOS/distribution/blob/f8cac7b92040d734506e238f5a44560a4f0e81b0/packages/hardware/quirks/devices/Powkiddy%20RGB30/050-audio_path#L5-L9)

実機の経路を切り替えてFEからGB版『Aretha』を起動した。音量20%で内蔵スピーカーからゲーム音が聞こえることをユーザーが確認した。この試験ではPCMのハードウェアポインターも進行した。

ARM64 Dockerで生成したSYSTEM `68b32b11fbe94b4672533cc95108de9ad6e3d8ebe5e0bf57a86674119c80e8ea` を既存SDへ差分適用し、試験起動後に既定へ設定した。起動時に `HP` が選ばれ、FEから『悪魔城伝説』を起動してRK817のPCMが `RUNNING` で進行した。ゲーム中に実機の音量ボタンが使う `gpio-keys` へ上下の入力を送り、音量値は4→5→4、左右のソフトウェア音量は143→146→143と変化した。試験後は20%でゲームを再生したままにした。

## RGB30のメニューショートカット

内蔵コントローラーのSELECT＋BをRetroArchのメニューに、SELECT＋STARTをPicoArchと単体エミュレータの既存メニューに割り当てた。ランチャーの動作中だけ、2つのキーの組み合わせを既存の `BTN_MODE` 入力として送る。RetroArchのSELECT＋STARTは従来の終了操作に使う。機種判定は `Powkiddy RGB30` を対象とする。

ARM64 Linuxの試験では、両プロファイルで押下順、単独押下、リピート、解放、イベント欠落、終了時のキー解放を確認した。

RGB30では既存SDから試験起動し、ランチャー経由で起動したエミュレータへ内蔵ゲームパッドと同じ入力デバイスからショートカットを送った。DRMの画面キャプチャで以下を確認した。

| エミュレータ | 組み合わせ | 実機結果 |
| --- | --- | --- |
| RetroArch（QuickNES） | SELECT＋B | Quick Menuの表示とゲームへの復帰。SELECT＋STARTで正常終了 |
| PicoArch（QuickNES） | SELECT＋START | Resume／Save／Exitメニューの表示とゲームへの復帰 |
| DraStic | SELECT＋START | DraSticメニューの表示 |
| PPSSPP | SELECT＋START | ポーズメニューの表示 |
| YabaSanshiro | SELECT＋START | Yaba Sanshiroメニューの表示 |
| OpenBOR | SELECT＋START | 『Dragon Ball』のプレイ中にPAUSE、Continue、End Gameの表示 |
| PCSX-ReARMed（単体版） | SELECT＋START | 『PAC-MAN WORLD』『チョロQワンダフォー！』は起動。メニューは表示されず。合成前の `BTN_MODE` を直接入力した場合も同じ結果 |

PCSX-ReARMedに同梱されているSDL互換ライブラリを使った実機の入力試験では、`BTN_MODE` がボタン10として読み取れた。単体版の実行ファイルにもボタン10のメニューバインドがある。ゲーム中のメニューが開かない原因は未確定。

## SSHパスワード認証

公開鍵認証に加え、Bubbleと同じrootアカウントでパスワード認証を使える。SYSTEMの組み立て時に、同じリビジョンのBubbleビルドからrootのシャドウエントリーを取り込み、Dropbearをパスワード認証有効で起動する。

ARM64 Docker内のDropbearで、パスワード認証と鍵認証、誤ったパスワードの拒否を確認した。

メニューショートカットとSSH認証を含むSYSTEMのSHA-256は `5fe5b1e5cbb0b5254727c52632ac511f8306eb22a874fc288d3b08d38b28ce0e`。パッケージ内のrootエントリーはBubbleのビルド入力とバイト単位で一致した。既存SDへSYSTEMを差分適用し、再起動後のRGB30に、SSHクライアントの公開鍵認証とキーボード対話認証を無効にした状態で、シリーズ共通のパスワードを使ってrootでログインした。

試験中は一時的に開いたSSH経由のADBを使用した。繰り返し試験でFEを停止した回数がplumOS initの再起動上限に達したため、修正版を既定に設定して本体を再起動した。試験鍵と登録スクリプトを削除し、試験鍵での接続が拒否されることと、再起動後にもパスワードでログインできることを確認した。Bubbleのプロセス、p5とSD2の読み書きマウント、試験前の実行時音量18/20を確認した。直前のSYSTEMはp4に保管した。

## RetroArchの既定アスペクト比

全機種共通のRetroArch設定は `aspect_ratio_index = "22"`（Core Provided）。Game Gearでも既定でこの設定を使い、LCDシェーダーを有効にしたまま、起動時のCustom指定を省く。ユーザー設定と、診断用に環境変数で明示した `sega43` と `integer3x` は使用できる。[RetroArch v1.22.2のアスペクト比定義](https://github.com/libretro/RetroArch/blob/v1.22.2/gfx/video_defines.h#L34-L61)

Docker生成のSYSTEM `5e7e5ac71cfeb2de5ad3739ede87d888336a200311ccc35ab120c3b4932f5d2a` を既存SDに差分適用した。RGB30でGame Gearの『Columns』とNESの『悪魔城伝説』をFEのランチャー経由で起動し、両方でCore Providedを読み込み、起動設定にアスペクト比の上書きがないことを確認した。ログ上でコアが返した比率はそれぞれ1.333と1.306。Game GearではLCDシェーダーが読み込まれた。分離した試験設定で既存の4:3指定が維持されることと、明示的に `integer3x` を選ぶとCustomになることも確認した。

720×720の内蔵パネルでは、Game Gearの表示範囲は720×540で上下90 pxの余白、NESの描画面は720×551で上端84 pxだった。試験後に修正版を既定に設定し、Bubbleの起動、p5とSD2の読み書きマウント、音量18/20への復帰を確認した。

## Scrapingの複数ROM取得

RGB30のFEログでは、NESの120本を認識しても1回につき2本しかCRC照合されなかった。空の画像索引でBusyBox awkを呼ぶと、2つのCRCワーカーがそれぞれ処理中のROM一覧を標準入力から末尾まで消費した。修正前は8本の試験で2本だけを照合し、修正後は同じ8本をすべて照合して7枚を保存した。

修正したスクリプトで実際のNESライブラリを再取得した。既存4枚はSHA-256が一致し、追加の照合116本から103枚を保存した。最終結果は120本中107枚。未取得の7本は使用したDATでCRC不一致、6本は一致したタイトル名のBox Art URLがHTTP 404だった。ライブラリを変えずに試したGBのスナップとGame Gearのタイトル画像でも、それぞれ6本すべてを照合し、4枚と5枚を取得した。

Docker生成のSYSTEM `9d8949af1fc5babf62feba2ece44abf223ddb84a7e35b328be340af450a40925` を既存SDに差分適用した。同梱版でも空のキャッシュを使ったNESの8本試験で8本を照合して7枚を取得した。FEが使うライブラリスキャンで実際のNESライブラリを照合し、120本中107枚を認識した。修正版を既定に設定し、Bubbleの起動とp5・SD2の読み書きマウントを確認した。

## 720×720のギャラリー配置

RGB30では従来、中央カードの上端がRG353Mと同じ84 pxに固定され、棚の背景から大きく離れて見えた。正方形のパネルでは、640×480のカード下端354 pxを画面高に比例させて配置する。実際の描画関数を使った座標試験では、RGB30の中央カードは上端261 px、下端531 px、左右のカードは上端306 pxだった。640×480の中央カードは上端84 px、下端354 pxだった。

Dockerで生成したSYSTEM `ca59db0c9f0d419b50fcfb43125c5a47c4267fe5dd79eb04948e337cef8e9d8a` を既存SDに差分適用した。RGB30のNESギャラリーで左右のカード移動を確認し、『Argus』の画像を新旧で比較した。中央カードの枠は177 px下がり、タイトルの帯は同じ位置だった。修正版を既定に設定した。

## RGB30のDraSticメニューとフレーム間隔

利用者の報告では、ゲーム画面を残したままメニューに入力が入り、Bでゲームに戻った。RGB30のSELECT＋STARTには、上流SDL2の設定メニューと、plumOSのキー変換で開くDraSticメニューの両方が反応し得た。RGB30ではDraSticの入力処理がこの組み合わせを1回だけ受け取り、ネイティブメニューへ渡す。SDL2内でSELECT／STARTの同時押しを消費するため、もう一方の設定メニューは同じ操作を受け取らない。

Bubble `96f9fa7` とV90S `e0b4b8f` の描画待ちの分離を参考にした。DraSticでは描画ランナーがKMSの画面切り替えを待つ前に、データを伴わないFLIPコマンドの受信を返す。SDL2側とランナー側の共有データはrelease／acquireで同期する。MFのDraStic実機記録 `cc7908d` と、JELOS 20240206のRK3566設定も確認した。

報告後の実行中セッションでは、DRMの画面更新が12秒で約55.5 fps、更新間隔の最長は約67 msだった。分離した実機試験では『New スーパーマリオブラザーズ』のタイトル付近で旧版59.50 fps、修正版59.56 fps。メニュー復帰後は旧設定の自動フレームスキップで約12 fpsまで落ちる区間を再現した。修正版で自動フレームスキップを無効にした比較は約44 fps、PCMはRUNNINGを維持した。3Dスレッド化の有無では約45.8／45.9 fpsで、今回の比較で大きな差はなかった。これらはDRMの画面更新数であり、コア内部の描画数とは区別する。

RGB30では工場出荷時の `frameskip_type = 2`／`frameskip_value = 4` の組み合わせを、最初のDraStic起動時にバックアップして自動フレームスキップを無効にする。移行後のユーザー設定、ゲーム別の設定、別機種での初期値が維持されることを確認した。

Docker生成のSYSTEM `d35a21157c344ee81123c1ba45352be8ec316e29ffd119ff76d511ed83434af1` を既存SDへ差分適用し、試験後に既定に設定した。標準のFEランチャーで『New スーパーマリオブラザーズ』をRGB30で起動した試験では、タイトル付近の15秒で59.65 fps、最長16.75 ms、ALSA PCMはRUNNINGだった。SELECT先押しとSTART先押しの両方でネイティブメニューが表示され、Bの後は両方でPCMと画面更新が復帰した。復帰直後を含む6秒と8秒の区間はそれぞれ54.42 fpsと43.11 fpsで、長い更新間隔が残った。分離した試験設定の移行とバックアップを照合し、利用者のセーブファイルが同じSHA-256であることを確認した。

### DraSticメニューの描画順

実機から再発報告を受けた時点のDRM画面には、プレイ中のゲームが止まったまま表示されていた。DraSticのSDL2を追うと、メニューを描く前の100 msの待機中に、残っていたゲーム画面の更新がメニュー表示フラグを消せる構造だった。そのフラグは、描画済みのメニューフレームをビデオスレッドが送る条件にもなっていた。

RK3566では固定の待機を外し、ネイティブメニューの描画完了を独立したアトミックフラグで通知する。ビデオスレッドはその通知を優先し、残っていたゲームフレームを破棄してメニューを表示する。Bでゲームに戻って新しいゲームフレームが来たときに、メニュー表示状態を解除してゲーム画面を描き直す。DockerのDraSticソースビルドに同じパッチを追加した。

RGB30でFEから『New スーパーマリオブラザーズ』を起動し、複製したステート0をDraSticのメニューから読み込んだ。ゲーム内でSELECT先押し6回、START先押し6回を交互に試した。12回ともDRMキャプチャにメニューが表示され、Bで同一セッションのゲーム画面と画面更新が復帰した。読み込み後の2秒区間はDRM更新43.85 fpsで、内蔵スピーカーのALSA PCMはRUNNINGだった。今回の変更は表示順を対象としており、ゲーム中のフレーム間隔のばらつきは観測された。

Docker生成のSYSTEM `377ee4a39338ac8267dda167727e0e4390f59ba245236fdc4c63be7739aba7e0` を既存SDへ差分適用し、試験後に既定に設定した。実機のDraStic SDL2のSHA-256はビルド出力と一致し、利用者のステート0は試験前後で同一のSHA-256だった。

### FPS表示中のメニューと通常プレイのフレーム間隔

FPS表示を有効にした実行中セッションのメモリでは、ネイティブメニュー用の256行すべてが `089.1% 100.0% 0.00m/0.00m` 形式の統計文字列で埋まっていた。メニューを開いたときに `Change Options` などの識別行を追加できず、描画するメニューを決められなかった。RK3566ではFPS統計を先に振り分け、描画スレッド上でのみFPS用サーフェスを差し替える。メニュー表示時はFPSの描画を止め、保留中のゲームフレームを破棄する。

通常プレイでは、コアが約60 fps相当の頻度でフレームを生成しても、生成間隔は一定でなく、画面への転送が完了するまで次のフレームを受け取れない場合があった。実行中セッションでは、描画に関わる2スレッドが5秒間に合計94,393回切り替わっていた。映像スレッドと共有メモリの待機をfutex通知に切り替え、描画中と書き込み中の領域を分けた。完成したゲームフレームを最大2枚、生成順に保持し、満杯のときは最も古い保留フレームを置き換える。今回の変更でCPUガバナー設定を変えていない。

RGB30でFEから『New スーパーマリオブラザーズ』を起動し、毎回同じステート0を複製して読み込んだ。以下はFPS表示を無効にした通常プレイ22秒間のDRM画面更新の比較で、液晶の更新間隔は約16.7 ms。ALSA PCMはRUNNINGを維持した。

| 構成 | DRM更新 fps | 25 ms超の間隔 | 最長 |
| --- | ---: | ---: | ---: |
| 従来版 | 49.23 | 141回 | 66.85 ms |
| 通知待ちと完成フレーム1枚 | 55.81 | 77回 | 50.14 ms |
| 通知待ちと完成フレーム2枚 | 59.44 | 7回 | 33.46 ms |

32ビットの送信側と64ビットの受信側をRGB30で動かし、新しい共有メモリで20,000往復の同期と内容一致を確認した。Dockerビルドで両方のバイナリを更新する。

Docker生成のSYSTEM `27b25285d42a906779d7d544766cfe1c06964b941054a1aae7f93c5ce415490c` を既存SDへ差分適用した。FPS表示を有効にした最終ビルドでも同じ場面の22秒間で59.01 fps、25 ms超は16回、最長33.45 msだった。DRMキャプチャでFPS表示を確認してから、SELECT先押しとSTART先押しを各6回試した。12回ともメニューが前面に表示され、Bで同じセッションに戻った。設定のサブメニューを開いて戻り、Exit DraSticで終了コード0とBubbleへの復帰を確認した。利用者のステート0は試験前後で同じSHA-256だった。最終SYSTEMを既定に設定した。
