出荷イメージに同梱された公開鍵で署名を照合した。Dockerでは公開済みイメージから取り出したSYSTEMを使い、利用者と同じ `PLUMOS/updates/` に配布用アーカイブを置き、フロントエンドの `START → System Settings → System Update` で選択した。適用と `runtime_healthy` を確認し、更新後の5ファイルをマニフェストのハッシュと照合した。Apps設定にPPSSPPが追加され、ランタイムの `VERSION` は `0.2.1` になった。再起動はDocker内で模擬した。

以前の同名アーカイブはバージョン表示だけを検証した別のファイルで、今回配布するアーカイブの識別には上記のSHA-256を使う。[以前の更新経路の検証](2026-11-27-rg353m-v0.2.1-update.md)

ADBで接続したRG353Mの起動元は先行イメージだった。実機の `/flash/SYSTEM` は `5439d0705e84c91b5b647b012ddbccecc90de725687ca605439026c47066a053` で、公開版のSYSTEM `a9c32fe2483143290c4a8ec4c3dd8c6b647c6015db1a5a063ec31c8bf7a0d022` と異なる。実機には先行試験の592バイトの更新ファイルが残り、ランタイムは適用済みの `0.2.1` だった。今回の更新試験は公開版v0.2.0のSDカードに切り替えて行う。

## 公開版v0.2.0のUSB ADB

利用者が公開版v0.2.0を書き込んで起動した後、MacはUSB 2.0ハブ経由で `2207:0006` とADBインターフェースを認識した。ADB 37.0.3ではMacからの `CNXN` に端末からの `CNXN` が返った直後、MacのUSB受信エンドポイント `0x81` が `0xe00002ed`（transaction error、転送0バイト）になり、シェル接続前にトランスポートが切れた。LIBADBUSB、LIBUSB、NATIVEの各方式でシェルを開けず、ADB 36.0.2でも端末一覧に残らなかった。端末の再起動とNW ServicesでのADBの再切り替え後にも再現した。

先行イメージと公開イメージの間で、カーネル、DTB、ブート設定、`init`、`start-adb`、`adbd`、ネットワークサービスのスクリプトは一致した。同じMacでは先行イメージでシェル接続できた。

Wi-Fi経由のSSHでRG353Mに接続し、OSとランタイムはともに `0.2.0`、`/flash/SYSTEM` のSHA-256は公開版と一致することを確認した。障害中も本体のUSBコントローラーは `configured`、速度は `high-speed` で、`adbd` はFunctionFSの3エンドポイントを開いていた。本体のログにもMacの接続要求が届き、認証不要と判定した記録が残った。SSHからPID 1の再バインドを要求し、`adbd` のPIDの変化とUSBの再構成を確認した。Mac側のADBをその後に起動してもシェル接続は復旧しなかった。

利用者が同じUSBハブの別ポートへ差し替えたところ、公開版v0.2.0のまま、MacのADBシェルとファイル転送が復旧した。元のポートでの途切れがポート固有か、差し替えによるUSBの再接続で解消したかは未特定。

## RG353Mの実機更新

公開版v0.2.0からの起動をSYSTEMのSHA-256とランタイムのバージョンで照合した。利用者用ボリュームに残っていた先行の592バイトのアーカイブを退避し、今回の配布ファイルを `PLUMOS/updates/` に転送してSHA-256を照合した。利用者が実機の `START → System Settings → System Update` を選ぶと、本体が自動再起動してフロントエンドが戻った。

再接続したUSB ADBで、boot IDの変化、ランタイム `0.2.1`、`runtime_healthy`、保留データの解消を確認した。実機の更新ログに残ったアーカイブのSHA-256と、適用した5ファイルのSHA-256は配布物と一致した。AppsにPPSSPPの起動設定が入り、p5とSD2はいずれも読み書き可能だった。ベースOSと同梱公開鍵は更新前と同じだった。
