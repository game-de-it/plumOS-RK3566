# RG353Vの共通SD起動とSD2

RGB30 r1・r2で起動確認したSDをRG353Vへ移した。実機のデバイスツリーは `Anbernic RG353V` で、TF1からplumOS initとBubbleが起動し、USB ADBで接続できた。SDのCIDのハッシュとp1のSHA-256はRGB30で採取した値と一致した。

カーネルはTF2のSDXCを `fe2c0000.dwmmc` で検出し、FAT32のパーティションを `/dev/mmcblk2p1` として認識していた。plumOSの `manage-sd2` が許可する機種にRG353Vが入っていなかったため、マウント処理が実行されなかった。

実機でスロットの割り当てを確認し、RG353Vを既存のSD2マウント処理に追加した。DockerのSYSTEM生成では、このスクリプトが標準で格納される。

## 実機試験

修正版のSYSTEM `4fea45cfbb11f268c067a0ae8a0121164bead2681d817a7b3b182c1af6eecf82` をUSB ADBで試行起動した。起動時にSD2が `/run/media/sd2` に読み書きマウントされ、ROMとBIOSが `/storage/user/Roms` と `/storage/user/BIOS` に公開された。BubbleとUSB ADBが起動し、修正版を既定に設定した。更新前後でp1、カーネル、RG353V用DTB、extlinux設定のSHA-256と、物理ストレージのパーティション一覧が一致した。

カーネルはSD2のFATに前回のアンマウントが正常に完了しなかったという警告を出した。Bubbleはこのカードのライブラリーキャッシュを利用し、キャッシュに含まれるSD2上の842件のパスがすべて存在することを実機で確認した。

試行起動の際、利用者はUSBケーブルを接続したままだと電源を入れられなかったと報告した。起動後のUSB ADBは動作した。電源投入時の挙動は原因未確定。

## 更新済みの共通IMG

同じSYSTEMを既存の共通IMGの生成経路に入れ、`output/rg353v-validation/sd2/plumOS-RK3566.img.gz` を生成した。DockerでFAT、ext4、GPT、p5の初回作成、SYSTEMの更新と復旧の検証に合格した。
