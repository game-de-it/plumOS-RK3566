## 表示とランタイム

- FEの初期設定と翻訳、エミュレータの起動経路、Appsの説明、診断メッセージを整理した。Pyxelの既定プロファイルは `pyxel:rk3566`。SD2、Wi-Fi、ストレージ診断、Python、Pyxelのヘルパー名とRetroArchの設定名称も揃えた。既存のp4に旧名のRetroArch設定がある場合は、初回に新しい名前で引き継ぐ。
- `plumOS-Bubble` の出典とコミット、GKDのライセンス通知、Music Playerの実機入力名判定、PortMasterの `GKD Bubble` 互換プロファイルを確認した。配布するFEの翻訳に `Bubble` の一致はなかった。ランタイム中の一致するパスは由来を記したライセンス通知 `licenses/bubble-vendor-runtime-NOTICE.txt` のみだった。
- 196のFE起動経路、表示されるApps、9コンポーネントのチェックサムを検証した。DockerではRetroArch 1.22.2のARM64実行、FEがPyxelのテスト項目から `plumos-pyxel-launch` を組み立てること、pygameの44.1 kHz・16 bit・ステレオの初期化、RGB10 Max 3のSDIO条件と他機種のWi-Fi経路を確認した。

## ブートと署名付き更新

- 前回試験版との比較で先頭16 MiB、末尾のGPT、p3のカーネル・DTB・extlinux・起動ロゴが一致した。RTL8723DSドライバー、plumOS init、機種専用SDL2も一致した。イメージ内のSYSTEMをビルド成果物と照合し、圧縮IMGがraw IMGとバイト単位で一致することを確認した。
- p5の初回作成、再起動後のセットアップ継続、既存データの保持、SYSTEMの試行起動と復旧をDockerで確認した。
- 更新の機種IDは `rk3566`、ファイル名形式は `plumos-rk3566-runtime-*.tar.gz`、同梱公開鍵のパスは `share/update/plumos-rk3566-update-public.pem`。公開鍵は工場出荷用SYSTEMから読み込み、追加のキー登録は行わなかった。
- 最終IMGから読み出したSYSTEMをDockerで展開し、FEのテキスト表示で `START → System Settings → System Update` を選択した。正式鍵で署名した検証用 `0.2.1-qa` を検出して再起動要求を出すこと、次回起動に相当する `apply-pending` でバージョンと追加ファイルが反映されることを確認した。正常確定前の再起動相当では `rolled_back`、再適用と正常確定後には `runtime_healthy` を確認した。別の鍵で署名したパッケージは拒否され、旧ファイル名形式は検出されなかった。[更新の検証スクリプト](../../prototype/verify-rk3566-update.sh)

Dockerではハードウェアの再起動を模擬した。続いてRG353M実機でこのイメージからの起動と、標準System Updateによる自動再起動、`0.2.1-qa` への更新を確認した。v0.1.xからv0.2.0への上書き更新用パッケージはこの試験に含まない。[RG353M実機の検証記録](2026-11-27-rg353m-v0.2.1-qa-update.md)
