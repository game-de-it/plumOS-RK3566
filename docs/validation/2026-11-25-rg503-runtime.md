## エミュレータ

RG353Vと同じ検体を使った。エミュレータの設定・セーブは試験中だけRAMに分離し、音量を4/20に設定した。CPUは標準の `ondemand` を使った。196プロファイル中、ゲームや起動素材を用意できた174件でDRMのフレーム提示と表示の更新を確認した。残る22件は指定ROMセット内に対応する検体がなかった。[RG503の全プロファイルの試験表](rg503-emulator-matrix.tsv) · [RG353Vの試験基準](2026-11-25-rg353v-runtime.md)

172件で内蔵スピーカー向けPCMのハードウェアポインターが進んだ。2048とTI-83では試験区間を通してPCMは `PREPARED`。Virtual Jaguar、MicroW8、Mupen64Plus-Next、Beetle PC-FX、Beetle Saturn、UzeboxでXRUNを観測した。いずれもRG353Vで発生していたコアで、Virtual Jaguarは18.20、MicroW8は21.20、Beetle PC-FXは33.75、Beetle Saturnは24.03、Uzeboxは30.54 fps。内蔵音声の結果はALSAの再生状態に基づく。[RG353VのXRUNと負荷の追加調査](2026-11-25-rg353v-audio-followup.md)

Mr.Boomは画面が更新され、計測区間では53.92 fpsで内蔵PCMが進み続けた。約10秒の起動停止と新しい停止ログは観測されなかった。

## スリープ復帰

USB給電中に電源メニューから `mem` / `s2idle` に入り、RTCで復帰した。Bubble単体ではboot IDとFEプロセスが一致した。RetroArch gpSP、PicoArch QuickNES、PCSX-ReARMed、PPSSPP、DraStic、YabaSanshiro、OpenBOR、Pyxelと、Music Player、File Manager、RetroArchメニュー、Game Gear、PortMasterの計13件で、メニューから復帰後も同じ描画プロセスが動作し、DRMの表示面に戻った。

OpenBORとMusic Playerは再試験で、復帰前後とも内蔵PCMの進行を確認した。FE側のScraping、Pyxel Setup、Update PortMaster、Repair SD2の4画面でも同じFEへ復帰し、Bで終了した。各回の復帰にはRTCを使用し、復帰後の入力は実機のevdevに送った。Wi-Fi SSHは復帰後に再接続できた。USB DACの試験は別日程。

## 最終起動

エミュレータと電源の試験でFEを繰り返し一時停止したため、試験中にplumOS initのFE再起動上限に達した。試験用SYSTEMを既定に設定して再起動し、別のboot IDで同じSYSTEM、BubbleとSD2が復帰することをWi-Fi SSHで確認した。

PCSX-ReARMedのFNメニュー、PortMasterのB操作、Game Gearのfpsと、SD2に残したPSX検体は[追加試験の記録](2026-11-25-rg503-pcsx-portmaster-gamegear.md)を参照。

## DraStic速度表示の再調査

SYSTEM `2ef03de4a4b984bc33352686c78f6103770b5b29976f26c643a3e6a5b2d4b61c` で、利用者が起動していた『New スーパーマリオブラザーズ』のワールドマップを計測した。DraStic本体・描画ランナー・双方のSDL2は、RGB30のCPU対策版 `f76e1c72bfe3202213140f914d7a7f9f37e26c23315823f0fe47a173bafc8499` とSHA-256が一致した。RG503ではCPU0〜CPU3がオンラインで、`cpufreq-dt` の `cpuinfo_cur_freq` とクロックツリーの `pll_apll`／`armclk` は1,992 MHzだった。ガバナーは計測開始時の `performance` のまま。設定ファイルの自動フレームスキップ値は `2/4` だったが、起動中のゲーム設定は `0/4` でフレームスキップは無効だった。

23秒間に液晶のVBlankは1,402回、DRMの画面更新は1,394回。更新は59.93 fpsで、間隔が25 msを超えたのは8回、最長33.21 msだった。DraSticの速度表示は86.03〜118.09%（中央値100.05%）で、描画率は全標本で100%。内蔵画面の更新とエミュレータ内の短時間の速度表示は別々に変動していた。USB DACのPCMは全221標本で `RUNNING`、再生開始時刻は一定、待ち行列の中央値は6,374フレームだった。別の8秒間のシステムコール標本で、DraStic主スレッドがDACの物理PCMを待つ20 msタイムアウトの `poll` を観測した。

後続の比較では、設定とセーブのコピーを一時領域に置き、同じROMをBubbleから起動した。フレームスキップ無効、音量4/20で、同じPIDのまま内蔵スピーカーからUSB DACへ切り替えて各約23秒を計測した。試験用セッションでは速度表示が無効だったため、比較対象はDRMの画面更新とPCM。

| 音声出力 | DRM更新 fps | 25 ms超 | 最大間隔 | PCM |
| --- | ---: | ---: | ---: | --- |
| 内蔵スピーカー | 60.01 | 6回 | 33.24 ms | 221標本すべて `RUNNING` |
| USB DAC | 59.97 | 7回 | 33.20 ms | 221標本すべて `RUNNING` |

画面更新の差はこの比較で0.04 fpsだった。両方とも液晶の実測は60.27 Hzで、最大33 msはVBlankを1回またぐ長さに相当する。`poll` の観測だけでは速度表示の変動原因を特定できない。試験後はセーブと設定の一時マウントを外し、音量15/20とUSB DACの経路を復元し、Bubbleへの復帰を確認した。

### フレームスキップの既定値とALSAの再生周期

出荷用 `drastic.cfg` の `frameskip_type` を `0` に変更した。旧出荷時の設定と一致する既存のグローバル設定は、次回起動時に一度だけ移行する。新規設定、旧出荷時のコピー、調整済みのグローバル設定、移行済みのRGB30、ゲーム別の設定を用いた確認を行った。

DraSticのARMHFコアはエミュレーションスレッドから同期的にALSAへ書き込む。従来の物理PCMは2,048フレームごとの再生周期で、44.1 kHzでは約46.4 msに相当する。DraSticの起動時のみ256フレーム（約5.8 ms）を上限として機器と交渉し、従来のバッファ容量を使う。短い周期でPCMを開けない機器では、クライアントの元のパラメーターで再試行する。

RG503上で、フレームスキップOFF、CPU設定とUSB DACを共通にし、『New スーパーマリオブラザーズ』のゲーム選択画面で同じプロセスのままALSAの期間を切り替えた。各区間で約16秒のDRM更新と速度表示を記録した。

| 再生周期 | DraStic速度表示の最小〜最大 | DRM更新 fps |
| --- | ---: | ---: |
| 2,048フレーム | 56.84〜120.05% | 58.75 |
| 512フレーム | 96.22〜103.41% | 60.09 |
| 256フレーム | 99.25〜101.66% | 60.15 |
| 2,048フレームに戻した区間 | 99.00〜101.17% | 60.03 |

別試験ではゲーム選択後の画面で2,048と256を交互に比較した。256フレームで揺れが小さくなった区間がある一方、USB DACの再初期化直後に約382 msの画面更新間隔が発生した区間もあった。再初期化の直後を除いた最大間隔はこの区間で33.22 ms。短い周期は音声の待ち時間を細かくするが、速度表示が振れる要因には場面や音声出力の切り替えも関わる。

修正版SYSTEM `5327e6d18fcb04f1b5ebf63a63052d8909d290e6dbb285d094c056e0ad735236` を既存SDへ差分転送し、試行起動した。Bubbleから通常起動すると、旧既定設定が移行され、DraSticの `Frame skip type` は `none` と表示された。USB DAC、内蔵スピーカー、USB DACの順にソフトウェアで出力を切り替え、同じPIDで各経路が256フレーム周期、PCM `RUNNING` になることを確認した。USB DACで59.97 fps、内蔵スピーカーで60.09 fps、画面更新間隔の最大はそれぞれ33.21 ms、33.30 msだった。

同じ修正版で速度表示を一時的に有効にした区間では、速度98.73〜101.84%、描画率100%、DRM更新59.97 fpsだった。画面更新間隔は最大33.25 msで、USB DACのPCMは全151標本で `RUNNING` だった。速度表示と音量を試験前の値に戻し、メニューから終了コード0でBubbleへ戻った。試験前後で利用者のセーブのSHA-256が一致した。修正版をRG503の既定に設定した。

### USB DAC切り替え後のDraSticの音飛び

『New スーパーマリオブラザーズ』のW1-1マップで再度計測した。CPU0〜CPU3はオンラインで、DraSticのCPUアフィニティは `0-3`、`performance` の適用中にCPUクロックツリーが1,992 MHzだった。DACを挿したままでもXRUNが起こり、メインスレッドのALSA `WRITEI` が最大191.08 ms続いた。別の標本では、8,192フレームの物理バッファに対して最大14,678フレームの書き込み要求を観測した。

MFの `b5bd9a8` は実際のPCMバッファ容量を使った位置計算、`8416892` と `6bf4d72` はUSB切断後のポーリング復旧、`7d0d134` と `b1ed6e4` はSDLの復帰時に空のPCMを再始動する対策。Bubbleの `96f9fa7` は描画の待ちを分離して音声との干渉を抑えていた。DraSticはALSAへ直接書き込むため、切り替えとXRUN復旧時は無音による先行書き込みを省き、論理PCMの位置を合わせ直す。ハードウェアの待ち合わせは256フレームのまま、実際のゲーム音が2,048フレームに達してから再生を始める。

試験版でUSB DACのデバイスをソフトウェアで再列挙した。DraSticのPIDは両方向で一致。内蔵スピーカーとDACのそれぞれで切り替え後24秒間、PCMの再生位置が進み、XRUNを観測しなかった。続いて物理的にDACを抜き、同じPIDで内蔵PCMが再生を開始した。利用者も音の復帰と、直後10秒ほどの間に音飛びやスロー再生がなかったことを確認した。最初の物理的な再挿入にはSYSTEMの転送と照合が重なり、約5秒後からPCMの再開とXRUNを観測したため、この区間は切り替えのみの評価から除外した。

ARM64とARMHFの音声ルーターをDockerでビルドし、SYSTEM `96a4f767191c8f6468183743d8442b0c1e571f63c2d3145d18550cbc2c6d9fa4` を既存SDへ差分転送した。修正版から起動して同じクイックセーブを読み込み、本体内のDRMトレースと75 ms間隔のPCM標本で、USBの状態を固定したまま処理負荷を比較した。MacでUSB ADBは列挙されず、比較にはWi-Fi SSHを使用した。ログの回収は計測終了後に行った。

| 計測区間 | DRM更新 fps | DraStic速度表示の最低値 | PCMの再開 |
| --- | ---: | ---: | ---: |
| 転送前の10秒 | 59.77 | 96.59% | 0回 |
| SSHでSYSTEMを24 MiB読み出し（6.86秒） | 56.62 | 80.89% | 2回 |
| 転送直後の10秒 | 59.97 | 90.63% | 0回 |
| RG503上でSYSTEMのSHA-256計算（10秒間） | 58.77 | 84.68% | 1回 |

DACの抜き差しがなくても、読み出しや照合の間に画面更新の低下とPCM再開が発生した。計測を始めた直後にも、転送中とは別にXRUNが1回あった。USB ADB自体の負荷は未計測。日常の切り替え試験では、SYSTEMの転送と照合を済ませてからゲームを起動する。

転送終了後、ソフトウェアでDACを無効化・再列挙し、同じDraStic PID 8807のまま内蔵スピーカーとDACのそれぞれで切り替え直後から再生を確認した。切り替え後の各20秒間はともに60.02 fpsで、PCMはそれぞれ全264標本で `RUNNING`、再生開始時刻は一定だった。切り替えから2秒以内の画面更新間隔は最大33.21 ms。物理的なDAC再挿入後の聴感確認は転送と重なったため、独立した判定を保留した。

試験後はDraSticのメニューからBubbleへ戻り、試験用設定の一時マウントを外した。保存済みクイックセーブのSHA-256を確認し、旧SYSTEMを復旧用に残した状態で修正版を起動の既定に設定した。

利用者が修正版のRG503でDraSticをプレイし、USB DAC接続時と内蔵スピーカー使用時の両方で、fpsが安定し、音飛びがないことを確認した。
